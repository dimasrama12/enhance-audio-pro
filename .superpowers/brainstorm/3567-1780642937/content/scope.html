Audio Conversion Feature — Planning Scope

The conversion feature has a significant existing foundation. What is the goal of this development plan?

Context

Already built: Python FFmpeg processor (16 formats), FastAPI /convert endpoint, Rust IPC commands, per-job Format/Bitrate/Sample Rate dropdowns in the UI, SQLite schema columns, Zustand store actions, and basic tests.

A

Gap Audit & Completion

Map exactly what is implemented vs. what is missing or broken. Build a plan to complete and harden what exists — no redesign, just finish it properly.

Pros

  • Fastest path to working feature
  • No wasted existing code

Cons

  • May carry over design flaws
B

UX Enhancement + Hardening

Keep the existing architecture but layer on improved UX — output preview, batch format override, codec-specific settings (VBR/CBR), and robust progress/cancellation flows.

Pros

  • Real feature value uplift
  • Builds on what works

Cons

  • More scope, more planning needed
C

Full Production Spec

Treat this as a greenfield design — ignore what exists, write a comprehensive production-grade spec covering the entire feature end-to-end, then reconcile with the existing code.

Pros

  • Best long-term foundation
  • No hidden gaps

Cons

  • Most work, may discard good code
